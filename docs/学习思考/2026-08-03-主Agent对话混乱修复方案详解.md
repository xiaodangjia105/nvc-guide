## 一、修复方案总览

本次修复包含三个层级，从底层数据到上层提示词，形成完整的防护链：

```
┌─────────────────────────────────────────────────────────┐
│                    P2: AgentLoop                        │
│            工具结果注入（即时防护）                      │
│    工具返回空结果时 → 注入系统指令阻止幻觉               │
├─────────────────────────────────────────────────────────┤
│                    P1: System Prompt                    │
│            工具描述优化（规则层防护）                    │
│    扩展触发词 + 强化失败处理规则 + 禁止编造              │
├─────────────────────────────────────────────────────────┤
│                    P0: 消息持久化                       │
│            工具调用记录保存（根本修复）                  │
│    TOOLCALL → TOOL消息 + toolCallsJson                  │
└─────────────────────────────────────────────────────────┘
```

## 二、P0：保存工具调用记录到对话历史

### 2.1 问题回顾

**修复前的数据流**：

```
第 1 轮对话：
  用户: "我总结过哪些关于心理学的笔记"
  AgentLoop: wiki_search("心理学") → "没有找到相关内容"
  AgentLoop: LLM 生成回复 "看起来你之前可能尝试搜索过..."
  
  保存到 DB：
    ┌─────────────────────────────────────────────┐
    │ seq=0  role=USER     content="我总结过..."   │
    │ seq=1  role=ASSISTANT content="看起来你..."  │ ← 工具调用记录丢失！
    └─────────────────────────────────────────────┘

第 2 轮对话：
  用户: "我的个人笔记"
  ContextManager 从 DB 加载：[用户消息1] + [助手回复1] + [用户消息2]
  
  LLM 看到的上下文：
    ┌─────────────────────────────────────────────┐
    │ 用户: "我总结过哪些关于心理学的笔记"          │
    │ 助手: "看起来你之前可能尝试搜索过..."         │ ← LLM 不知道调用过 wiki_search
    │ 用户: "我的个人笔记"                          │
    └─────────────────────────────────────────────┘
  
  → LLM 不知道第 1 轮已经搜过 → 重复调用 wiki_search → 幻觉
```

**修复后的数据流**：

```
第 1 轮对话：
  用户: "我总结过哪些关于心理学的笔记"
  AgentLoop: wiki_search("心理学") → "没有找到相关内容"
  AgentLoop: LLM 生成回复 "你的个人知识库中暂时没有找到..."
  
  保存到 DB：
    ┌──────────────────────────────────────────────────────────────┐
    │ seq=0  role=USER     content="我总结过..."                    │
    │ seq=1  role=TOOL     content="调用工具: wiki_search(...)"     │ ← 新增
    │ seq=2  role=TOOL     content="工具 wiki_search 执行成功: ..." │ ← 新增
    │ seq=3  role=ASSISTANT content="你的个人知识库中暂时没有..."    │
    │          toolCallsJson=[{"toolName":"wiki_search",...}]       │ ← 新增
    └──────────────────────────────────────────────────────────────┘

第 2 轮对话：
  用户: "我的个人笔记"
  ContextManager 从 DB 加载并转换为 Spring AI Message：
  
  LLM 看到的上下文：
    ┌──────────────────────────────────────────────────────────────┐
    │ User: "我总结过哪些关于心理学的笔记"                           │
    │ Assistant(toolCalls=[wiki_search]): "..."                     │ ← LLM 知道调用过
    │ ToolResponse(wiki_search): "没有找到相关内容"                  │ ← LLM 知道结果
    │ Assistant: "你的个人知识库中暂时没有找到..."                    │
    │ User: "我的个人笔记"                                          │
    └──────────────────────────────────────────────────────────────┘
  
  → LLM 知道第 1 轮已经搜过且没有找到 → 不会重复调用 → 如实告知用户
```

### 2.2 实现细节

#### 2.2.1 NvcAssistantService — 事件收集与保存

**核心改动**：将 `doOnNext` 中只保存 `CONTENT`，改为保存所有关键事件。

```java
// 收集工具调用记录
final ConcurrentLinkedQueue<Map<String, Object>> toolCallRecords = new ConcurrentLinkedQueue<>();
final ConcurrentLinkedQueue<AgentEvent> pendingToolStarts = new ConcurrentLinkedQueue<>();

Flux<AgentEvent> processedStream = eventStream
    .doOnNext(event -> {
        switch (event.type()) {
            case TOOLCALL_START -> {
                // 1. 记录到临时队列（等待配对的 TOOLCALL_END）
                pendingToolStarts.add(event);
                // 2. 保存 TOOL 消息到 DB
                saveToolMessage(convId, userId, event.data(),
                    "调用工具: " + event.data() + "(" + event.metadata().get("arguments") + ")",
                    seqCounter.getAndIncrement());
            }
            case TOOLCALL_END -> {
                // 1. 配对 TOOLCALL_START
                AgentEvent startEvent = pendingToolStarts.poll();
                // 2. 记录到 toolCallRecords（用于 ASSISTANT 消息的 toolCallsJson）
                toolCallRecords.add(Map.of(
                    "toolName", toolName, "success", success,
                    "result", truncate(result, 500), "durationMs", durationMs
                ));
                // 3. 保存 TOOL 消息到 DB
                saveToolMessage(convId, userId, toolName, resultSummary,
                    seqCounter.getAndIncrement());
            }
            case CONTENT -> {
                // 1. 将 toolCallRecords 序列化为 JSON
                String toolCallsJson = objectMapper.writeValueAsString(toolCallRecords);
                // 2. 保存 ASSISTANT 消息（附带 toolCallsJson）
                saveAssistantReply(convId, userId, event.data(), toolCallsJson,
                    seqCounter.getAndIncrement());
                toolCallRecords.clear();
            }
        }
    })
```

**关键设计决策**：

| 决策 | 理由 |
|------|------|
| 用 `ConcurrentLinkedQueue` 收集事件 | Flux 的 doOnNext 可能在不同线程执行，需要线程安全的集合 |
| 用 `AtomicInteger` 替代 `final int` | seq 需要在 lambda 中递增，Java 要求 lambda 变量 effectively final |
| TOOL 消息和 ASSISTANT 消息分开保存 | TOOL 消息用于构建 ToolResponseMessage，ASSISTANT 消息的 toolCallsJson 用于构建 ToolCall |
| toolCallsJson 存在 ASSISTANT 消息上 | 与 OpenAI API 格式一致，方便后续对接 |

#### 2.2.2 ContextManager — 消息加载与转换

**核心改动**：将 `toMessage` 方法从跳过 TOOL 消息，改为正确转换。

```java
private Message toMessage(NvcAssistantMessageEntity entity) {
    return switch (entity.getRole()) {
        case USER -> new UserMessage(entity.getContent());
        case ASSISTANT -> {
            // 如果有 toolCallsJson，构建带工具调用的 AssistantMessage
            if (entity.getToolCallsJson() != null && !entity.getToolCallsJson().isEmpty()) {
                yield buildAssistantMessageWithToolCalls(entity);
            }
            yield new AssistantMessage(entity.getContent());
        }
        case SYSTEM -> new SystemMessage(entity.getContent());
        case TOOL -> {
            // TOOL 消息转为 ToolResponseMessage
            if (entity.getToolName() != null) {
                yield ToolResponseMessage.builder()
                    .responses(List.of(new ToolResponseMessage.ToolResponse(
                        entity.getToolCallId() != null ? entity.getToolCallId() : "tool-" + entity.getId(),
                        entity.getToolName(),
                        entity.getContent()
                    )))
                    .build();
            }
            yield null; // 缺少必要字段，跳过
        }
    };
}
```

**数据转换映射**：

```
DB 记录                              →  Spring AI Message
─────────────────────────────────────────────────────────────
role=USER, content="..."             →  UserMessage("...")
role=ASSISTANT, content="..."        →  AssistantMessage("...")
role=ASSISTANT, toolCallsJson=[...]  →  AssistantMessage("...", toolCalls=[...])
role=TOOL, toolName="wiki_search"    →  ToolResponseMessage(responses=[ToolResponse(...)])
role=SYSTEM, content="..."           →  SystemMessage("...")
```

### 2.3 带来的好处

| 好处 | 说明 |
|------|------|
| **消除重复工具调用** | LLM 知道之前调用过什么工具，不会重复调用已失败的工具 |
| **消除幻觉回复** | LLM 能看到工具返回的"没有找到"，不会编造不存在的内容 |
| **对话连贯性** | LLM 能理解完整的对话上下文，包括工具调用和结果 |
| **调试可观测性** | DB 中保存了完整的工具调用记录，方便排查问题 |

### 2.4 潜在影响

| 影响 | 说明 | 应对 |
|------|------|------|
| 消息数增加 | 每次工具调用增加 2 条 TOOL 消息 | ContextManager 已有压缩机制（20 条阈值） |
| 上下文 Token 增加 | TOOL 消息内容可能较长 | truncateResult 限制 2000 字符，TOOL 消息内容限制 200 字符 |
| DB 存储增加 | 每次对话多存 2-6 条消息 | 消息量级较小，无需额外优化 |
| 旧数据兼容 | 旧的 ASSISTANT 消息没有 toolCallsJson | ContextManager 做了 null 检查，旧数据正常处理 |

## 三、P1：优化 System Prompt

### 3.1 问题回顾

**修复前的工具描述**：

```
## wiki_search — 搜索个人笔记
**触发词**：我的笔记、之前的记录
```

用户说"我总结过哪些关于心理学的笔记"时，LLM 不确定该用 `wiki_search` 还是 `rag_search`，因为：
- "心理学"不在 `wiki_search` 的触发词中
- "笔记"不在 `rag_search` 的触发词中
- LLM 在不确定时可能随机选择或同时调用多个工具

### 3.2 实现细节

**修复后的工具描述**：

```
## wiki_search — 搜索个人笔记/知识库

**触发条件**：当用户提到以下任何一种情况时调用：
- 明确说"我的笔记""个人笔记""之前的记录""搜索笔记"
- 说"我总结过""我记录过""我学过""我收藏的"
- 说"个人知识库""我的知识库""看看我有没有"
- 任何涉及"我的...笔记/记录/总结"的请求

**结果处理**：
- 如果返回"没有找到相关内容"，如实告知用户"你的个人知识库中暂时没有找到相关内容"
- 不要因为没找到就去调用 rag_search 或其他无关工具
```

**新增核心原则**：

```
4. **工具调用失败或返回"没有找到"时，必须如实告知用户，
    然后询问用户是否要尝试其他搜索词。绝对不要换一个不相关的工具继续调用。**
5. **绝对不要编造用户没有提到的内容。如果不知道答案，就说不知道。**
6. **回复必须基于工具返回的实际结果，不要凭空想象。**
```

### 3.3 带来的好处

| 好处 | 说明 |
|------|------|
| **工具选择更准确** | 扩展触发词后，LLM 能更准确地匹配用户意图 |
| **减少误调用** | 明确的"不要用于"规则，防止 LLM 错误选择工具 |
| **失败处理规范化** | 工具失败时 LLM 有明确的行为指引 |
| **幻觉抑制** | "不要编造"原则直接约束 LLM 行为 |

### 3.4 潜在影响

| 影响 | 说明 | 应对 |
|------|------|------|
| Prompt 长度增加 | 工具描述更详细 | 增量较小（约 200 tokens），可接受 |
| LLM 行为更保守 | 可能减少主动调用工具的倾向 | 这正是我们需要的——宁可不调用，也不要乱调用 |
| 旧 Prompt 缓存 | 如果有 Prompt 缓存机制 | 重启后自动失效 |

## 四、P2：AgentLoop 工具结果上下文注入

### 4.1 问题回顾

即使有了 P0 和 P1，LLM 在同一轮内连续调用多个工具时，仍然可能忽略前一个工具的失败结果。例如：

```
Turn 0:
  LLM 调用 wiki_search("心理学") → 返回"没有找到"
  LLM 不停下来告知用户，继续调用 rag_search("NVC理论") → 返回 NVC 知识
  LLM 最终回复 NVC 知识，而不是告知用户没找到心理学笔记
```

### 4.2 实现细节

**在 AgentLoop 中，当工具返回空结果时，注入明确的系统指令**：

```java
// 工具结果消息（注入明确指令，防止 LLM 幻觉）
String responseText = result.skipped()
    ? "跳过: " + result.skipReason()
    : (result.success() ? result.result() : "Error: " + result.result());

// 当工具返回空结果或"没有找到"时，注入明确指令
if (result.success() && isEmptyResult(result.result())) {
    responseText = result.result()
        + "\n\n[系统指令] 搜索结果为空。请如实告知用户未找到相关内容，"
        + "并询问是否要尝试其他搜索词。不要调用其他无关工具，不要编造内容。";
}

toolResponses.add(new ToolResponseMessage.ToolResponse(
    tc.id(), tc.name(), responseText));
```

**isEmptyResult 判断逻辑**：

```java
private boolean isEmptyResult(String result) {
    if (result == null || result.isBlank()) return true;
    String lower = result.toLowerCase();
    return lower.contains("没有找到")
        || lower.contains("未找到")
        || lower.contains("no results")
        || lower.contains("not found")
        || lower.equals("[]")
        || lower.equals("{}");
}
```

### 4.3 带来的好处

| 好处 | 说明 |
|------|------|
| **即时防护** | 在工具返回的瞬间就注入指令，不依赖 LLM 的理解能力 |
| **同轮防护** | 即使 LLM 在同一轮内连续调用多个工具，也能在每次工具返回后注入指令 |
| **兜底机制** | 即使 P0/P1 失效，P2 仍然能阻止幻觉 |

### 4.4 潜在影响

| 影响 | 说明 | 应对 |
|------|------|------|
| 工具结果内容变长 | 注入的指令约 50 tokens | 仅在空结果时注入，频率较低 |
| LLM 可能过于保守 | 注入指令后 LLM 可能完全不尝试其他工具 | 这是预期行为——用户问的是个人笔记，不应该被引导到 NVC 知识 |
| 误判空结果 | 某些工具可能返回包含"没有找到"的正常内容 | isEmptyResult 做了精确匹配，误判概率低 |

## 五、三个方案的协同关系

```
用户: "我总结过哪些关于心理学的笔记"
         │
         ▼
    ┌─────────────────────────────────────────────┐
    │ P1: System Prompt                           │
    │ "我总结过" → 触发 wiki_search               │
    │ "心理学" → 搜索个人知识库                    │
    └──────────────────┬──────────────────────────┘
                       │ LLM 决定调用 wiki_search
                       ▼
    ┌─────────────────────────────────────────────┐
    │ P2: AgentLoop                               │
    │ wiki_search 返回"没有找到"                   │
    │ → 注入指令："如实告知用户，不要调用其他工具"  │
    └──────────────────┬──────────────────────────┘
                       │ LLM 如实告知用户
                       ▼
    ┌─────────────────────────────────────────────┐
    │ P0: 消息持久化                               │
    │ 保存 TOOL 消息 + ASSISTANT 的 toolCallsJson  │
    │ 下一轮 LLM 能看到完整的工具调用历史          │
    └─────────────────────────────────────────────┘
```

**协同效果**：

| 层级 | 作用 | 防护时机 |
|------|------|----------|
| P1 (Prompt) | 引导 LLM 正确选择工具 | LLM 决策前 |
| P2 (AgentLoop) | 工具返回后注入指令 | 工具执行后 |
| P0 (持久化) | 保存完整历史供后续轮次使用 | 下一轮对话前 |

三层防护形成闭环：P1 减少错误决策，P2 在错误发生时即时纠正，P0 确保错误不会在后续轮次中重复。

## 七、总结

| 方案 | 核心思想 | 实现难度 | 效果 |
|------|----------|----------|------|
| P0 | 让 LLM 有记忆 | 中 | 根本修复 |
| P1 | 给 LLM 更好的指引 | 低 | 减少错误决策 |
| P2 | 在错误发生时即时纠正 | 低 | 兜底防护 |

**一句话总结**：P0 解决"LLM 不知道之前发生了什么"，P1 解决"LLM 不知道该怎么做"，P2 解决"LLM 做错了怎么办"。三层协同，从根本上消除对话混乱问题。
